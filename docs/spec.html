Retain Feedback

Publish written Retain App Store reviews as issues in Retain-Feedback. Triage daily and create private Retain backlog issues for actionable feedback.

Assumptions and objective

  • One public feedback issue per written Apple review; no reviewer nickname. The Apple review ID identifies the source across reruns and edits.
  • Clear defects, regressions, and feature requests become private backlog issues. Generic praise stays public. Vague feedback remains visible for human triage.
  • One private backlog issue per actionable Apple review. A later review edit updates the bot-owned source section but preserves human notes.
  • No public App Store reply, AI service, app-code edit, or release is triggered by review content.

The rule-based classifier is intentionally conservative. It does not claim to understand every language or infer a reproducible bug from a star rating.

Flow and credentials

  1. A daily workflow on public Retain-Feedback uses a standard Ubuntu runner. GitHub says standard runners in public repositories are free. It also supports manual dispatch.
  2. A short-lived Apple ES256 token, scoped to GET /v1/apps/6816576807/customerReviews, reads all pages. The Apple Customer Support key lives only in repository secrets.
  3. The public repo's GITHUB_TOKEN creates and updates its own review issues. A separate GitHub App installed only on private Retain supplies a short-lived token with Issues read/write for backlog reconciliation.
  4. All existing public and private issues are scanned before writes. A stable Apple ID marker prevents duplicate issues after retries. Changed reviews reopen matching issues for triage without deleting human notes.
  5. The workflow records a compact daily status commit, including failed attempts, so a quiet public repo has ongoing activity. A failed import remains visibly failed.

Secrets are never written to the repository, issue bodies, workflow logs, or status files. The workflow never executes text from a review.

Triage rules

  • Promote a review that clearly describes a crash, failure, regression, lost data, or an explicit feature request. A 1–2 star review with specific negative feedback also creates an investigation item.
  • Do not promote generic praise, empty text, or vague criticism without a clear task. Mark such public issues for human review or no backlog as appropriate.
  • Private issue title names the suspected problem or request, not a confirmed diagnosis. Its body links the public feedback issue and records the rule that selected it.
  • Do not auto-close private issues when a review disappears or changes tone. Mark edits for renewed human triage.

Project shape and commands

scripts/app_store_reviews.py reads and reconciles reviews; scripts/triage_reviews.py classifies and reconciles backlog issues; tests/ holds offline fixtures; .github/workflows/ holds the daily job; docs/ holds this specification and the plan.

Offline tests: python -B -m unittest discover -s tests -p 'test_*.py'. Workflow check: actionlint .github/workflows/app-store-reviews.yml. Live check: manually dispatch on the default branch, then rerun and confirm zero duplicate issues.

Style: small Python functions, explicit API validation, no broad exception swallowing. Example: if review_id in existing: update_source_section(existing[review_id], review).

Acceptance and boundaries

  • Public repo exists with Issues enabled. First successful run backfills written reviews; second run creates no duplicates; edits update matching issues.
  • Only actionable reviews create private Retain backlog issues. Reruns and partial failures do not duplicate them. Public review text cannot execute code or spoof issue markers.
  • Apple and GitHub authentication failures fail visibly. Tests cover pagination, errors, classification, edits, and credential-safe logging.
  • Only standard public GitHub-hosted runners are used; no artifact or cache is uploaded. The private Retain repo hosts no review-intake Actions workflow.
  • Apple's Account Holder must personally accept API terms. Key issuance and GitHub App installation must be complete before a live run.
